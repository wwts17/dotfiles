# 交付产出质量评审规范 (Quality Review Rubric)

## 核心原则
遵循 **BLUF (结论先行)** 结构输出评审结果。坚持**“基于事实与证据 (Evidence-Based)”**原则：先列出具体文件/行号中的客观事实证据，再判定评级，严禁凭主观感觉评分。

## 离散评级定义
- **良好 (Pass)**：符合全部工程标准，无阻断性缺陷，可直接交付生产。
- **待改进 (Needs Improvement)**：可正常运行/理解，但存在非阻断性的规范、可读性或边界优化空间。
- **不合格 (Reject)**：存在阻断性缺陷（如逻辑错误、误导性描述、严重安全/性能隐患或无法复现）。

## 分项 Rubric 检查清单

### 1. 技术文档评审 (Technical Documentation)
- **结构**：是否结论先行 (BLUF)？是否遵循“摘要 ➔ 架构 ➔ 详细设计 ➔ 附录”渐进式分层？
- **精准度**：路径、命令、参数符号是否精准可跑？是否存在“大概”、“可能”等含糊用语？
- **完备性**：是否包含非目标 (Non-Goals) 及方案权衡与副作用分析？

### 2. 工程实施计划评审 (Implementation Plan)
- **目标与范围**：是否明确为什么做、变更文件清单及具体 Diff 预期？
- **可验证性**：是否提供明确的自动化测试命令与手动验证步骤？

### 3. 代码与 Commit 提交评审 (Code & Commits)
- **代码规范**：显式错误处理、零值可用、无过度抽象与无效注释。
- **Commit 规范**：符合 Conventional Commits，说明“变更原因”而非仅描述“做了什么”，无 AI 署名。

### 4. Skill 规范 / Prompt 评审
- **触发精度**：`description` 语义表达是否能被 LLM 精准触发。
- **内容密度**：语言言简意赅，无黑话废话，思维工具行数控制在 $\le 35$ 行。

## 标准评审输出模板

```markdown
### 评审结论 (Executive Summary)
- **综合判定**：[良好 / 待改进 / 不合格]
- **核心结论**：[一句话说明整体质量与是否建议交付]
- **阻断项 (Blockers)**：[无 / 仅不合格时列出必须修复项]

### 维度核对与证据链 (Detailed Evidence)
- **维度 A [评审维度]**：[良好 | 待改进 | 不合格]
  - 事实证据：[精确指到 文件:行号 或 章节:段落]
  - 改进建议：[具体可执行的修改建议]

- **维度 B [评审维度]**：[良好 | 待改进 | 不合格]
  - 事实证据：[精确指到 文件:行号 或 章节:段落]
  - 改进建议：[具体可执行的修改建议]
```
