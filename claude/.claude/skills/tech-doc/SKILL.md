# 技术文档写作

## 核心
文档服务读者的阅读路径，不是作者的思考路径：先核对事实再动笔，正文由浅入深，参考性内容下沉附录，单份交付即自洽。

## 适用场景
写、改写或重排要发给他人的技术文档：设计说明、技术方案、机制说明、接口说明。
不用：草稿、临时笔记、代码注释。交付前的质量自检交给 `quality-review`——本 skill 管怎么写，那份管怎么判。

## 规则

**动笔前先核对事实。** 每条断言指到代码符号、配置文件或建表脚本；指不到就查，查不到标"待确认"。改旧文档先列"文档说 X / 代码是 Y"差异清单，被证伪的旧结论显式改掉，不与新内容并存。
❌ 请求失败会自动重试几次 ✅ 失败重试 3 次，退避 1s/2s/4s（`RetryPolicy.MAX_ATTEMPTS`）

**区分当前值、约束与意图。** 环境里读不到的值（配置中心内容、生产库数据）只写约束与影响；未实现的计划必须标明。
❌ 各环境限流阈值已按 QPS 100 配好 ✅ 阈值由配置项 `rate-limit.qps` 决定，未配置时不限流；线上取值以配置中心为准

**章节由浅入深，每节只回答一个问题。** 骨架见范例。参考性长表（边界清单、术语表、错误码全集）下沉附录，正文只前置最必需的 2–3 个概念。
❌ 开篇 12 行术语表、接口章节前插 30 行边界表 ✅ 摘要 → 背景 → 概览 → 流程 → 关键设计 → 契约 → 附录

**同一事实只讲一次。** 重复内容留在更深的那一节，浅处删掉；决策与其落地物（表结构、配置项）相隔较远时加"见 x.y"指路。

**关键设计要写代价。** 按"解决什么问题 → 怎么做 → 副作用或已知缺口 → 收紧路径"写完整；只有优点的设计说明不可信。
❌ 改用消息队列解耦，天然削峰 ✅ 改用消息队列解耦；代价是消费端需自行保证幂等，重复投递会重复执行；收紧需引入去重表

**措辞：陈述式、术语统一、现在时。** 一个概念全文一个词，先定名再全文替换；字段名与错误码原样引用。
❌ 这块逻辑很坑 / 本次改为异步写入 / 用户与账号混用 ✅ 该分支存在竞态 / 写入为异步 / 全文统一为账号

**单份交付即自洽。** 默认读者只拿到这一份：不引用其他文档、不写相对上一版的差异。历史演进另存归档件并在开头标注状态；确需互引时在开头声明阅读顺序。

**图只画真实结构。** 时序图的消息必须是真实交互，状态变化与内部计算用自调用或 Note；参与方按系统边界划分。流程图节点形状固定语义：判定菱形、动作矩形、终态圆角，拒绝分支标真实错误码。
❌ `客户端->>服务端: 订单进入待支付状态`（状态不是消息） ✅ `支付网关->>服务端: 支付结果回调`

## 范例
说明类文档骨架，可直接照抄后逐节填：

````markdown
# <机制名>设计说明

- 摘要 3–5 条，每条一句讲清一条最重要的规则

## 1. 背景与目标      为什么做；只前置最必需的 2–3 个概念
## 2. 机制概览        七条以内，每条一个要点
## 3. 核心流程        3.1 端到端时序图  3.2 校验链流程图  3.3 计算规则
## 4. 关键设计        每节：问题 → 做法 → 代价 → 收紧路径
## 5. 接口            请求/响应示例 + 全部错误码
## 6. 数据表          DDL + 索引意图
## 7. 配置            应用配置 / 动态配置 / 缓存键
## 附录 A：边界情况   长表，按场景一行一条
## 附录 B：术语       长表，一个概念一行
````
