# Claude configuration

Stow package deployed to `~/.claude/`. Three layers, following the official memory/skills split:

- `CLAUDE.md` — hard rules, the writing rules for prose shown to the user (one line, `@shared/writing.md`, which Claude Code expands in place), the three silent-failure rules, and the toolchain; loaded every session. A rule earns its place here only if breaking it fails without anyone noticing.
- `skills/` — everything that loads on demand: coding, debugging, performance, tech-doc, git-commits.
- `skills-parked/` — skills removed from `~/.claude/skills` but kept in the repo: thinking and its four models (mece, first-principles, systems-thinking, probabilistic). Parked because they fired on ordinary implementation tasks and produced an analysis framework instead of a plan. Not stowed (`claude/.stow-local-ignore`); to restore one, move its directory back into `skills/`.
- `shared/review-standards.md` — what a review judges and how a finding is written: verdicts, the five-line finding format (`Severity` / `Introduced` / `Outcome` / `Fix` / `Where`) followed by a unified `diff` block — `-` lines quoted verbatim, `+` lines the rewritten code, standards, review dimensions, output format. `Introduced` other than `yes` forces Severity `Pre-existing`; `Outcome` states what an observer sees, and any mechanism — a class name, a variable, a derivation — belongs in Notes instead. Not a skill; it never fires on its own. Both this package's reviewer and Antigravity's read it.
- `shared/writing.md` — how prose written to the user reads: reply in Chinese, terms only from the project's code, the framework's docs, or standard Chinese, conclusion first, one idea per sentence, no coined nouns, no metaphors, no emoji. Not a skill either; `CLAUDE.md` imports it with `@shared/writing.md` so it is resident every session. Covers review reports and implementation plans, not code or commit messages. Shared with Antigravity through the `shared/` symlink.
- `agents/reviewer.md` — pre-delivery review in an isolated context. A thin shell over `shared/review-standards.md`, adding only the `first`/`recheck` mode that `/quality-review` drives; reads the skill files it needs rather than restating them.
- `commands/feature.md` — `/feature`: deliver a feature end to end, one step finished before the next starts. Clarify with the user, read the affected code, write a Plan or a Design, wait for every Decisions-needed answer, implement step by step (a Design stage by stage, each stage gated on a review and committed before the next), then a final cross-stage review for a Design. The step list is the file; this line does not restate it.
- `commands/quality-review.md` — `/quality-review`: review finished changes without editing them, as a `first` round or a `recheck`. Runs the built-in `/code-review` and `agents/reviewer`, writes their full output plus a `## Decisions` ledger to `~/.claude/reviews/<repo>/<branch>-<round>.md`, and puts four sections in the chat — 要修, 你定, 上线前你去核实, 已驳回 — with the report path and nothing else. The ledger is what makes a `recheck` cheap: an item the user deferred or refused is not argued a second time. The rules are the file; this line does not restate them.

## Plan or Design

Plan when the change touches at most 3 files and adds no new data model; Design otherwise. Design adds a Spec section (behavior contract table, interface signatures, data structures) that the reviewer and the tests are checked against. Defined in `skills/tech-doc`; the `/feature` command applies it at step 3. Design also adds Stages — the implementation split into independently reviewable stages — and the per-stage review gate that `/feature` enforces at step 5.

## Maintenance conventions

- Single source of truth: define content in one place; other files reference it by path only. This is also the source for the Antigravity package: `antigravity/.gemini/` symlinks `CLAUDE.md`, the five shared skills, and `shared/` into this directory — see `antigravity/.gemini/README.md`. What gets shared is decided by whether the content is about engineering or about the harness: engineering content is the same under both tools, so it lives here once; anything naming a command, a mode, or a report path belongs to one tool and stays in that tool's own file. That is why `agents/reviewer.md` is a shell around `shared/review-standards.md` rather than a shared file itself. The cross-references are: `agents/reviewer` → `shared/review-standards`; `shared/review-standards` → `skills/coding`, `skills/git-commits`, `skills/tech-doc`; `commands/feature` → `skills/tech-doc`, `skills/coding`, `skills/git-commits`, `commands/quality-review`; `commands/quality-review` → the built-in `/code-review`, `agents/reviewer`; debugging and performance → the coding skill.
- A file the Antigravity package links to describes engineering, never this harness. A slash command, a review round, or a `~/.claude` path is correct for one tool and dead text for the other; it belongs in that tool's own file. `scripts/doctor.sh` derives the shared set from the symlinks and fails on the wording, so the check needs no list to keep up to date.
- Conventions and "always do X" content go in CLAUDE.md; multi-step procedures go in skills. Don't copy one layer into the other.
- Anything that must apply while writing code belongs in a skill, not in `~/.claude/rules/`. Both load; a rule file loads every session, a skill only when its description matches. Use `rules/` only for text that must be present in every session and is too big for CLAUDE.md.
- An agent's `skills:` frontmatter injects the full skill body at startup (verified against 2.1.263 with a marker-phrase probe; 2.1.247 had reported nothing preloaded). The reviewer still reads skill files at run time instead of listing them: preloading charges every review for all three skills, a run-time read charges only for the one the change needs.
- A skill description states when to use the skill. It never lists the body's rules — copies drift apart, and a `## When to use` section that only restates the description is dead weight.
- A skill takes one of two shapes and keeps to it. A convention skill (`coding`, `git-commits`, `tech-doc`) is Rules plus worked ❌/✅ examples. A procedure skill (`debugging`, `performance`) is When to use — including what it is *not* for — then Steps, a one-line `Not:` for the tempting wrong move the steps do not already rule out, then Output. Don't add a section a skill has nothing to put in.
- CLAUDE.md never maintains a list of skills. Descriptions are already visible to Claude; hand-written lists go stale.
- A skill fires on its description alone, so it will not fire for work that does not look like its trigger. `disable-model-invocation: true` in the frontmatter would hide a skill from the model and leave only `/name`; the knowledge skills deliberately do not use it. `commands/feature` does, because it edits code and commits — a workflow with side effects is started by the user, not by the model. `commands/quality-review` stays model-invocable: it only reads code and writes a report.
- Every rule carries its own test: a countable threshold, an observable trigger, or a pair of ❌/✅ examples. A rule that cannot answer "how would I know I broke it" is not admitted — it takes up room without changing behavior.
- Apart from the hard rules and the silent failures, every rule is a default rather than a prohibition. Deviate when there is a reason, and state the reason. The point of a rule is to make deviation a deliberate decision, not to prevent it.
- A long prompt typed over and over means a missing entry point, not a missing skill. Put the content in the existing units and the call sequence in a `.claude/commands/` macro: skills carry content, commands carry invocation.
- Before adding anything, ask which existing scenario it belongs to. Only a genuinely new scenario justifies a new file.
- Wording: plain professional English; quote original authors verbatim where their phrasing is the point; no invented shorthand.
- After changes: run `/doctor` (config health) and `/context` (resident context cost) in a fresh session. After changing `commands/quality-review.md` or `shared/review-standards.md`, also run `/quality-review` once on a real branch and check the chat report against `fixtures/quality-review-sample.md` — `/doctor` proves the files load, not that the output has the right shape. `fixtures/` is not stowed.
